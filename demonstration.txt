1. REMOTE-WORK ELIGIBILITY

Say: "I will check policy evidence and the mock employee record, but I will not
claim that the employee is eligible unless the policy and all required facts
support that conclusion."

Request:
POST /api/demo/remote-work-eligibility
The configured demo message is:
"Am I eligible to work remote from Finland? employee ID DEMO-1002"

The orchestrator detects the remote-work eligibility workflow. Since the
request includes an employee ID, it selects structured profile data; the
workflow also requires policy evidence and a mock compliance check. It calls
these MCP tools, in order:

1. lookup_employee_profile
   Arguments: employee_id="DEMO-1002"
   Output: {"employee_id":"DEMO-1002","name":"Mock Employee",
   "department":"People Operations","location":"Helsinki",
   "employment_status":"active"}
   This is a fixed mock result, not a lookup in data/employee_profiles.csv.

2. check_policy_compliance
   Arguments: query="<demo message>"
   Output: {"compliant":true,"status":"mock_check",
   "policy_source":"not specified",
   "reason":"Mock result; verify against current HR policy before acting."}
   The boolean is not an HR decision: the tool explicitly returns a mock
   warning, and the final answer does not treat it as proof of eligibility.

3. retrieve_policy
   Arguments: query="<demo message>" (top_k omitted; MCP default is 5)
   Output: one relevant local-index result:
   remote-001 / remote_work_policy.md / section "Remote work" —
   "Remote work requires manager approval and an approved secure workspace."

The final response is formatted as readable guidance, not as the synthesis
prompt. It quotes and cites remote-001, reports the profile as mock data, says
eligibility cannot be confirmed, and asks the user to confirm employing entity,
role, manager approval, team coverage, and security requirements with HR.
Finland-specific eligibility is not established by the available snippet.

2. PTO REQUEST GUIDANCE

Say: "For PTO, policy guidance alone is not enough to report a personal
balance. I will check the mock balance as well as retrieve the policy, then
explain how to proceed without implying the request was submitted or approved."

Request:
POST /api/demo/pto-request-guidance
The configured demo message is:
"Search the PTO policy and check my balance for next week. employee ID DEMO-1002"

The orchestrator detects the PTO workflow. The employee ID makes a balance
lookup relevant; the explicit search wording selects the document-search MCP
tool as well as policy retrieval. It calls:

1. check_pto_balance
   Arguments: employee_id="DEMO-1002"
   Output: {"employee_id":"DEMO-1002","available_days":18,
   "pending_days":2,"as_of":"2026-09-21"}
   These are fixed mock values and the displayed as-of date matters.

2. retrieve_policy
   Arguments: query="<demo message>" (top_k omitted; default 5)
   Output: pto-001 / pto_policy.md / section "PTO requests" —
   "PTO requests should be submitted through the approved HR channel before
   leave begins."

3. search_policy_documents
   Arguments: query="<demo message>" (top_k omitted; default 5)
   Output: the matching PTO policy result pto-001 with its source, section
   metadata, and snippet.

The final answer formats the balance as mock data, cites the exact PTO
snippet, and recommends confirming dates/type, arranging a handover, and
submitting through the approved channel before leave begins. It does not
represent the request as submitted, approved, or covered by unprovided
blackout/notice-period rules.

RAG-ONLY VERSUS STRUCTURED DATA OR MOCK ACTIONS

The route decision is deliberately simple and auditable. A policy explanation
that can be answered from the supplied policy snippets uses retrieval only.
Personal/current facts, such as an employee profile or PTO balance, require an
employee ID and select the corresponding structured-data MCP tool. A search
word selects search_policy_documents. Unsupported employee-specific facts are
not invented when the ID is missing. Mutating requests such as creating a
ticket are different again: create_mock_hr_ticket is held behind explicit user
confirmation.

For a confirmation example, ask: "Create a mock HR ticket for my PTO question.
employee ID DEMO-1002". The first response is a local preview with
status=confirmation_required; the MCP action is not called yet. After the user
presses Confirm action, the app calls create_mock_hr_ticket with query,
employee_id="DEMO-1002", and confirmed=true. The mock MCP output has
status=created_mock and a generated ticket_id in the form HR-XXXXXXXX. No real
HR system is changed.

RAG GROUNDING AND CITATIONS

- The chat app requests top_k=5. The current corpus has only three hand-authored
  local snippets; the MCP policy index has two. There are no metadata filters.
- Query rewriting is enabled in the app, but no synonym map is configured, so
  it currently leaves these demo queries unchanged.
- Reranking uses lexical overlap of non-stopword query terms, and unmatched
  snippets are discarded. This is keyword reranking, not a learned reranker.
- Chunking is manual: each record is a short, one-sentence synthetic snippet.
  The PDFs are not parsed or chunked into the live chat index. The section
  labels shown in citations are fixture metadata, not page/section locations
  extracted from those PDFs.
- No embedding model runs in the chat path. Local records contain placeholder
  two-number vectors, but the enabled lexical reranker determines these demo
  results. No semantic embedding is generated.
- Chat retrieval uses in-memory Python lists. scripts/init_vector_db.py can
  initialize a PostgreSQL/pgvector table, but the chat path does not populate
  or query it.
- Each final policy statement carries its chunk ID, source label, fixture
  section, and exact snippet; the API also returns citation metadata and
  snippets separately. For example:
  [pto-001; pto_policy.md; PTO requests] "PTO requests should be submitted
  through the approved HR channel before leave begins."

CI/CD AND MCP VERIFICATION

GitHub Actions in .github/workflows/ci.yml runs on push and pull request,
installs requirements.txt, and runs unittest discovery on Python 3.11 and
3.12. The MCP integration test, test_stdio_client_calls_the_real_mcp_server,
uses the stdio client to call tools/list and then call retrieve_policy; the
suite also checks the tool catalogue and protected mock-action confirmation.
render.yaml now sets autoDeployTrigger=checksPass on both Render web services,
so a provisioned Render Blueprint is configured to wait for successful checks
before automatic deployment. The app's MCP_SERVER_URL references the MCP
service's public url property, not its internal host: Render free web services
can make private-network requests but cannot receive them, so using the
internal host would break app-to-MCP traffic on this free-tier setup.

Spoken deployment verification:
